Card anatomy / schema types

Three types. Room for nuance.

English first, target language next. Type is implicit in the content and styling, not a label on the card. Word definitions stay close to the word. Topic context and register are not displayed on cards. Usage notes and examples belong in an expanded view, not these compact cards. The controls above apply here too.

Reusable format

One question. A runnable reference.

Follow the Pane Protocol model: a live example next to the reasoning. Unlike that settled protocol, this study presents alternatives; it does not establish application rules.

  1. Frame: name the surface, its grouping semantics, and non-goals.
  2. Explore: keep language and typography controls shared; use identical fixtures when comparing alternatives for the same purpose. Do not confuse conversation, vocabulary, and starred collections.
  3. Stress: include long and short content, alternatives, empty collections, narrow widths, and larger type.
  4. Observe: record device/browser, settings, and the specific failure or advantage.
  5. Decide: record accepted, rejected, and unresolved ideas before porting. Keep the runnable specimens as a visual reference.

Current scope: conversational topic groups, a word / phrase / sentence gallery, and mixed starred cards in Spanish, simplified Chinese with ruby pinyin, and Japanese with furigana or romaji. Type is explicit fixture data, not inferred from punctuation: generated conversation lines remain phrases. Out of scope: details panes, swipe actions, audio, backend/schema changes, and production integration.

Future studies: follow the shared exploration methodology. Create a separate directory under explorations/ for each concept, keeping its standalone HTML, fixtures, and assets local so studies can evolve independently.

Porting reference

Preserve hierarchy, not CSS.

  • Anatomy: English above the target. Japanese shows either original script with available furigana or romaji, never both. The Readings control toggles ruby annotations, not the selected script.
  • Typography: Latin target 20 px; CJK and Japanese romaji 23 px; English 14 px; ruby 0.48 em. Headwords use a stronger weight. The size control scales card text. These are exploration values, not approved native tokens.
  • Conversation: side and tint distinguish interchangeable voices. Swap exchanges sides, not order. JSON-encoded notes carry speaker and alternative metadata; “or” follows the same side as its options. Interleaved alternatives still need a separate grouping decision.
  • Starred collection: C combines words, phrases, and sentences. No topic context, type, speaker, or “or” marker appears on cards. Removing a star removes the entry; empty selection is intentional.
  • Interaction: stars have 44 × 44 CSS-pixel targets and pressed state. This artifact simulates only controls and stars, not production audio or details interactions.
  • Reading data: hand-authored base/annotation pairs, not automatic alignment. Unannotated kana and punctuation remain ordinary text. Chinese syllables pair with individual characters so readings stay attached while wrapping.
  • Native checks still required: iOS Safari ruby wrapping, VoiceOver order, Dynamic Type, and native font metrics. Browser scaling is not Dynamic Type. Have a fluent reviewer check fixtures before using them as teaching content. See the card schema.

Production references: web/app/src/components/card.js and conversation styles in web/app/src/styles/components.css. Gallery and C share the same compact anatomy: English, target, and optional word definition. Context and formality remain in fixture data but are not displayed on cards. Usage notes and examples remain in fixture data for expanded-card design; no expanded interaction is simulated here. Structured speaker metadata is never displayed as prose.
