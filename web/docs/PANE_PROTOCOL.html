Glossary

Read this section first. Every other rule uses these terms with the precise meaning given here. Past versions of the code use "pane", "drawer", "sheet", and "panel" interchangeably; this protocol settles the vocabulary.

Pane
The universal noun. A pane is any major surface the user sees. Specific kinds are navigation pane, content pane, details pane, action pane. Never use "drawer", "sheet", "panel", or "view" as synonyms. ("Sheet" survives only inside the action pane's implementation as .sheet-handle — that is historical CSS and acceptable.)
Layer
One of the four fixed z-stack positions in the application. There are exactly four layers, in this order from bottom to top: shell, content, details, action. A pane lives in exactly one layer. The stack order never changes (see Rule 8).
Navigation pane
Lives in the shell layer. Lists decks; sits underneath the content pane. Revealed by sliding the content pane sideways.
Content pane
Lives in the content layer. Shows the currently selected screen — a deck, a browse view, the empty state. Slides sideways to reveal the navigation pane underneath.
Details pane
Lives in the details layer. A bottom-anchored surface that slides up over a scrim and shows one item at a time (one card's full detail view). It is not full-height; the content pane it dims is visible behind the scrim. Horizontal swipe inside the details pane navigates to the previous or next sibling item without dismissing — the pane stays open, only the item changes. A back affordance (or a click on the scrim) closes the layer and returns to the content pane.
Action pane
Lives in the action layer. A bottom-anchored, modal surface that slides up over a scrim. Used for transient tasks: translation, generate cards, deck settings. Dismissed by swipe-down, scrim click, or an explicit close action. At most one action pane is open at a time.
Scrim
A semi-transparent overlay that dims the layers underneath when a higher layer is open. The scrim is interactive: clicking it dismisses the layer above it. Both the details pane and the action pane slide up over a scrim; the shell-reveal does not (full-height content simply slides aside to expose the navigation pane underneath).
Handle
A static DOM element that exists for the sole purpose of receiving touch gestures. A handle is always present in the same place relative to its parent layer; it is never created or destroyed by content changes. Examples: the top bar of the content pane (where the swipe-to-reveal-nav gesture lives), the drag-bar at the top of an action pane.
State / slice / namespace
The application has one shared state object. It is divided into named slices; each slice belongs to a namespace. A namespace is the string identifier (for example "shell", "content", "details", "action"); the slice is the value at that key.
Transition
A named, pure function that takes the current slice plus an optional payload and returns the next slice. The only blessed way to change state. Names follow the pattern namespace/verb, for example action/open.
Action (DOM)
An interaction declared on a DOM element via data-action="namespace/verb". The per-layer click handler reads this attribute and dispatches to the registered handler. Often, but not always, an action handler simply calls the transition of the same name.
Subscriber
A function registered against a namespace that runs whenever that namespace's slice changes. Subscribers read the new slice and write data-* attributes on DOM elements — they never rebuild the DOM.
Delegate
The single click listener attached to a layer's root element. The delegate routes clicks to action handlers via data-action. There is one delegate per layer (see Rule 5).

Why this exists

The Loudmouth web app is a mobile-first PWA built in vanilla JavaScript with no framework. Earlier code grew pane-by-pane, with each pane inventing its own way of holding state, wiring events, and reacting to gestures. The result was code that was about eighty percent right, fragile when neighbouring panes changed, and tedious to extend.

This protocol is the smallest set of rules that, when followed, produces panes that fit together without coordination. It exists so that any contributor — human or AI — can read the rules, implement a new pane, and have it behave correctly the first time without inventing infrastructure.

The single sentence summary: the app holds one shared state object split into named slices; panes declare what slice they own and what transitions they accept; the DOM is built once and then updated through attributes; one click handler per layer routes interactions; gestures animate motion under the finger but only commit changes on release.

The mental model — four layers

Picture the app as a stage with four stacked layers. The stack order never changes.

  1. Shell layer. The navigation pane. Lowest, always present, never dismissed. Visible only when the content layer is slid aside.
  2. Content layer. The content pane. Sits over the shell. Always present; the user navigates between content screens (a deck, a browse view, an empty state) by swapping what the content pane renders, not by adding new layers.
  3. Details layer. The details pane. Optional. Bottom-anchored and scrim'd; slides up over the content pane when the user drills into a single item, and is not full-height (the dimmed content shows behind it). Stays open across horizontal swipes — swiping left or right inside the details pane traverses to the previous or next sibling item from the underlying content list, without dismissing. A back affordance or a scrim click closes it.
  4. Action layer. The action pane. Optional. Sits over everything else. Bottom-anchored, modal, scrim'd. Used for transient tasks. At most one action pane open at a time. Action layer always wins the z-order — if a details pane is open and an action pane opens on top, the action pane is in front and the details pane remains intact underneath.

The shared state object has one slice per layer plus any other independent concerns (for example, which deck is currently selected for the content layer to render). Each slice has a single owner — a pane module — that defines the slice's shape and the transitions that move it between states.

Gestures animate motion under the user's finger. They temporarily move pixels. When the user lifts their finger, the gesture decides whether the motion crossed a threshold; if so, it calls a transition to record the new resting position. The state machine never sees the in-flight motion.

Rule 1 UI state lives in one place, organized by namespace

The application has exactly one state object. It is created at boot and lives for the life of the app. There are no per-pane state objects, no module-level mutable variables for UI state, no booleans hidden in closures.

The object is divided into named slices called namespaces. Every namespace is owned by exactly one pane module. The shell layer's pane owns shell. The content layer's pane owns content. The details pane owns details. The action pane owns action. Two modules trying to claim the same namespace is a registration error and the app should refuse to start.

Subscribers register against a single namespace, not the whole state object. When a slice changes, only the subscribers for that slice are notified. This is what makes the system tolerable as more panes are added — a shell toggle never re-runs content subscribers.

Change is signalled by reference equality on the slice object. Replacing a slice with a new object of identical shape but a different reference is a change; mutating a field inside an existing slice object in place is forbidden and will not notify anyone. The discipline is: always build the next slice as a fresh object (using spread or equivalent), then hand it to the state machine to install.

Rule 2 State only changes through named transitions

A namespace owner declares a set of transitions. A transition is a named operation that takes the current slice plus an optional payload and returns the next slice (or returns nothing to indicate the slice should be cleared). Transitions are registered at app boot.

Names are namespaced strings of the form namespace/verb — for example action/open, action/close, shell/toggle, content/select-deck, details/open, details/next, details/prev, details/close. Verbs are short, descriptive, and read naturally aloud. The slash is the separator and is part of the identifier.

Code that wants to change state calls the state machine with a transition name and a payload. It does not reach into the slice and write fields directly. This rule exists so that every state change is greppable, named, and reviewable in one pass.

Transitions are pure functions of (previous slice, payload). They do not perform side effects, do not touch the DOM, and do not call other transitions. Transitions only describe the next resting state.

Side effects (I/O, DOM writes outside the subscriber pattern, network calls, persistence) live in one of two places:

  • Subscribers for effects driven by state — "whenever the deck changes, fetch its cards"; "whenever a sheet opens, focus its first input." The subscriber is the natural home because the effect is downstream of a state change that other parts of the app may also see.
  • Action handlers for effects driven by direct user intent — "when the user confirms an edit, save the new order to IndexedDB"; "when the user taps Translate, call the API." The handler is the natural home because the effect is the point of the action, not a consequence of state having changed.

The dividing line: if the effect should also fire when state changes through a route other than the action (programmatic change, restored state, transition triggered by another pane), put it in a subscriber. If it only makes sense as a direct response to the user's tap or swipe, put it in the action handler. When in doubt, prefer subscribers — they are more composable.

Both surfaces have access to host.ui for reading state. Neither calls a transition during a side-effect's in-flight work; if the work needs to update state on completion, it calls the transition when it returns.

An unknown transition is an error in development and a silent no-op in production. A transition that returns the same reference as the previous slice is a no-op; subscribers are not notified.

Rule 3 Every pane follows the same contract

A pane module's default export is a single object with the following five fields. Every pane, without exception, exports exactly these fields as the default export. The pane may additionally have named exports for collaborator stubs (data fetchers, persistence helpers, pure utilities) that the pane itself uses internally — these are not part of the contract, but the protocol does not forbid them. What the protocol does forbid is putting state, transitions, or rendering logic in named exports — the default export is the only place those live.

  • namespace — the string this pane owns. Must be unique across the app.
  • initialState — the slice value this pane contributes when the app boots. May be null for panes that start empty (the details and action panes both start null).
  • transitions — the map of transition names to transition functions, as described in Rule 2.
  • render — a function that takes the initial slice and returns the full HTML string for the pane's root element, including any handles. Called exactly once, at mount time. Pure: no DOM access, no closures over mutable state, no side effects.
  • bindEvents — a function with the signature bindEvents(rootEl, host). The pane uses host to reach everything outside itself: the global state machine, its layer's delegate, and any siblings it needs to coordinate with. Inside bindEvents the pane registers click actions through its layer's delegate, subscribes to its own namespace (and any other namespaces it needs to react to), and wires touch gestures directly onto the static handles inside its root. Returns a cleanup function. The shape of host is:
    • host.ui — the state machine (get, subscribe, transition, etc.).
    • host.delegate — the delegate for this pane's layer (Rule 5).
    • host.parent — optional, the parent pane's bound interface if this pane is a child of another (e.g., a sheet inside a content pane). Most panes do not use this.
    The same host shape is passed to every pane. Panes never reach for globals or import other panes directly; if they need something not in host, the host shape is extended (a protocol change) rather than worked around.

Cleanup is invoked when a pane is unmounted. In version one, persistent panes (navigation and content) are never unmounted, so their cleanup is a no-op. Transient panes (details and action) do get unmounted, and their cleanup must remove all delegate registrations, all state subscriptions, and all gesture listeners they installed.

Rule 4 Render once, then update attributes

A pane's render function runs once when the pane mounts and produces the full DOM subtree as an HTML string. After that, the DOM is never rebuilt. All visible changes from state transitions happen by writing data-* attributes on existing elements, and letting CSS attribute selectors decide how those attribute values translate into visual changes.

For example: when the shell namespace transitions from foreground to background, the subscriber writes data-shell="background" on the stage element. A CSS rule of the form [data-shell="background"] .content-pane { transform: translateX(220px); } does the visual work. JavaScript never sets style.transform or style.display on the resting element, and never calls innerHTML a second time on the same container.

Every element a pane ever needs to show must be present in the HTML returned by render. Elements that should be hidden in some states are present in the DOM and hidden by CSS attribute selectors. There is no conditional omission of elements based on state.

Lists are the one exception. When the underlying data changes — a card is added, a deck is renamed — the list region may be re-rendered by replacing its innerHTML with a fresh string built from the new data. The list region is a stable container; the items inside it are disposable. Event handlers for items rely on delegation (Rule 5), so re-rendering items does not require re-binding handlers. Gestures rely on static handles (Rule 6), so re-rendering items does not require re-binding gesture listeners either.

Rule 5 One click handler per layer

Each layer has exactly one click listener, attached at boot to that layer's root element. The shell layer has its own delegate, the content layer has its own, details has its own, action has its own. There is not a single application-wide click handler — that would force every shell event through every content listener and would entangle layers that should stay independent.

Every clickable element in a layer carries a data-action attribute. When a click bubbles up to that layer's root, the layer's handler finds the nearest ancestor with a data-action value and dispatches to the function registered for that value.

Panes register their action handlers during bindEvents, against their own layer's delegate. Action names follow the same namespace/verb convention as transitions, and in many cases an action handler does nothing except call a transition with the same name. The action and the transition are different concepts — actions are how the user expresses intent through the DOM, transitions are how the state machine records that intent — but they often share a name for clarity.

Payload data for an action lives on the same element as data-action, in additional data-* attributes. For example, a deck row might carry data-action="content/select-deck" and data-deck-id="003-greetings". The action handler reads the relevant data-* values off the element it was given.

A pane never calls addEventListener('click', ...) on any element it owns. Clicks are routed entirely through its layer's delegate. Re-rendered list items keep working with no rebinding because the listener is on the layer root, which never re-mounts.

When a higher layer is open (action pane over content, for example), clicks on the higher layer's elements are caught by the higher layer's delegate first because of DOM hit-testing order. Lower layers are visually behind a scrim that intercepts clicks, so the situation does not arise in practice.

Rule 6 Gestures track the finger; transitions commit on release

Touch gestures (swipe, drag) are not delegated. They wire directly to static handles using touchstart, touchmove, touchend, and touchcancel. A static handle is a DOM element whose location and existence relative to its parent layer never changes for the life of the application — for example, the top bar of the content pane, the drag-bar of the action pane. Handles are written in the pane's render output once and never re-created. Gestures are wired once during bindEvents and never re-wired.

Gestures are never wired to dynamic content inside a pane (individual card rows, list items, or anything that gets re-rendered). If a piece of dynamic content needs a gesture, the pane provides a static handle that detects the gesture and uses event coordinates to identify which item was the target. The reason: re-rendering dynamic content would orphan any listeners attached to it.

Identifying the targeted item. When a static handle overlays dynamic content (a reorder handle covering a list of cards, for example), the blessed pattern is: on touchstart, temporarily set pointer-events: none on the handle, call document.elementFromPoint(x, y) to find the dynamic element underneath, then restore pointer-events on the handle so it continues receiving the rest of the gesture. The handle owns the gesture lifecycle; elementFromPoint is used only to identify which underlying item the gesture is acting on. Use closest() on the returned element to walk up to the meaningful row container, and read any data-* attributes (item id, index) you need from there.

A gesture is responsible for three things and three things only.

  1. Track the finger frame-for-frame. On every touchmove that belongs to the gesture, the moving element gets its position updated through an inline transform. The position responds to the finger, not to the state machine. This is the entire animation while the finger is down.
  2. Suppress CSS transitions during the drag. While the finger is down, the dragged element carries a data-dragging attribute. A CSS rule disables transitions while that attribute is present, so the inline transform reflects the finger exactly without animating.
  3. Commit or snap back on release. On touchend (and touchcancel), the gesture compares the final displacement against a threshold.
    • If the threshold was crossed, the gesture calls a transition to record the new resting state, then removes data-dragging. The transition's subscriber writes the new data-* attribute on the stage. CSS sees the attribute change with transitions re-enabled, and the element animates from its current dragged position to its new resting position. There is no jump — the element flows continuously from where the finger left it to where the state says it belongs.
    • If the threshold was not crossed, the gesture removes both the inline transform and data-dragging. CSS animates back to the original resting position (which the data attribute already encodes).

The gesture never calls a transition during touchmove. The state machine is only ever told about resting positions, never about in-flight motion. This keeps the rendering layer simple and keeps subscribers fast.

Axis lock is mandatory. On the first move that exceeds a small threshold (four pixels in either direction), the gesture decides whether the motion is horizontal or vertical. If the gesture only cares about one axis, motion on the other axis is ignored for the rest of the touch — including not preventing default — so that page scrolling is not disrupted.

Touch cancel is handled the same as a below-threshold touch end: snap back, remove data-dragging, do nothing else.

Rule 7 Subscribers never touch a dragging element

This is the protocol's load-bearing wall. State subscribers run whenever a slice changes. They write data-* attributes on elements. If a subscriber writes to an element while a gesture is in the middle of dragging it, the subscriber's write will fight the gesture's inline transform and produce visual chaos.

The rule is simple: before a subscriber writes anything to a DOM element, it checks whether that element (or any ancestor) has data-dragging set. If so, the subscriber defers the write until after the next touchend. The simplest implementation is a shared helper that subscribers call instead of writing attributes directly; the helper either writes immediately or queues the write to run when data-dragging is cleared.

In practice, this conflict is rare because Rule 6 forbids gestures from calling transitions during touchmove. The guard exists to make accidental violations harmless rather than catastrophic.

List regions get the same discipline. Rule 4 allows a designated list region to be re-rendered via innerHTML when its underlying data changes. That re-render is just as destructive as an attribute write — possibly more so, because it can replace the very element a finger is dragging. While a gesture is active on items inside a list region, the gesture must mark the list region itself with data-dragging, and any subscriber that rebuilds the region's innerHTML must check data-dragging on the region before rebuilding. If the region is mid-drag, the rebuild is deferred until data-dragging clears. The shared subscriber helper that handles attribute writes should also gate list rebuilds — same mechanism, same guard, applied to the region instead of an individual element.

Rule 8 Layer stack is fixed: shell < content < details < action

The four layers stack in a fixed order. Lower layers are visually behind higher layers; clicks on higher layers shadow lower layers. The stack order never changes at runtime.

  • The action layer is always on top. If a details pane is open and an action pane opens, the action pane sits above the details pane and the details pane is fully preserved underneath — when the action pane closes, the user returns to the same details pane in the same state.
  • The details layer sits above the content layer. The content pane is fully preserved underneath; closing the details pane returns the user to the same content scroll position and same selection.
  • The content layer sits above the shell layer. The navigation pane is preserved underneath the content pane and is revealed by sliding the content pane sideways, not by destroying it.

Stacking is not flexible. The protocol does not support "details over action" or any other reordering. If a future requirement seems to need it, the protocol must be revised — do not invent ad-hoc z-index gymnastics in a pane.

Sheets / action panes do not stack on top of each other. Opening an action pane while another is already open is an error and should be treated as "close the existing action pane, then open the new one" — never as stacking action panes on action panes.

Live example

Below is a working implementation that exercises all four layers. Use it to feel how the protocol behaves:

  • Shell. Tap the menu icon (top-left) or drag from the left edge of the content pane to expose the nav. The shell gesture lives on a dedicated invisible left-edge handle; once the nav is exposed, the handle expands to cover the whole pane so swiping back works from anywhere. Click the scrim or swipe back to close.
  • Content. Click a deck in the nav to switch which deck is displayed.
  • Details. Click a card row to open the details pane. Inside, two invisible full-height edge handles own the traverse gesture: drag from the right edge leftward to go to the next card, drag from the left edge rightward to go to the previous. The three card faces (prev / current / next) move together as a stack so siblings slide visually into view. The position indicator updates after each commit. Click the back chevron to dismiss the pane.
  • Action. Click the + floating action button (bottom-right of the content pane) to open the action pane. Dismiss by dragging the drag-bar downward, clicking the scrim, or clicking the close button inside.

Watch the transition log at the bottom — every state change is named and visible. No transitions fire during a drag; they all fire on release.

Applying the contract to a new pane

Suppose you need to add a new pane — say, a "Browse all cards" pane that shows a searchable list across every deck. The protocol tells you exactly what to do.

  1. Decide the layer. Browse replaces what the content pane is showing, so it lives in the content layer; it is a content-pane mode, not a new layer. If it were transient and modal it would be an action pane; if it overlaid a single item it would be a details pane. The layer choice is the most important early decision.
  2. Pick a namespace. Something like browse. Grep the codebase to confirm no other pane owns it. If browse is just a content-pane mode rather than a separate pane module, this step is replaced by adding fields to the content slice instead.
  3. Sketch the slice shape. What fields describe a resting state? A query string, a sort order, perhaps a selected card identifier. Write the shape as a comment in the pane file. Decide what initialState should be for a fresh boot.
  4. List the transitions. What named operations move the slice from one resting state to another? browse/query updates the search text. browse/sort changes the sort order. browse/select records which card is focused. Each is a pure function from previous slice plus payload to next slice.
  5. Write render. Return an HTML string for the entire pane root, including any static handles. Include all elements that any state could ever show; hide variants with CSS attribute selectors keyed off your namespace's data attributes. Do not branch inside render based on slice values except to set the initial data attribute on the root.
  6. Write bindEvents. Create the layer delegate (or get a reference to the existing one if this pane is part of an existing layer). Register click actions through it. Subscribe to your own namespace and write the appropriate data-* attributes when the slice changes. If the pane needs to react to other namespaces (for instance, dismissing itself when an action pane opens over it), subscribe to those too. If the pane needs touch gestures, wire them directly to the static handles inside the pane and follow Rule 6.
  7. Return cleanup. If the pane is persistent, return a no-op. If it can be unmounted, return a function that unregisters every action handler, every subscriber, and every gesture listener it installed.

That is the whole job. Anything else the pane needs — fetching data, calling the API, working with IndexedDB — happens inside transitions and subscribers but follows no special rule from this protocol. Use the existing utilities in src/js/.

Things this protocol explicitly forbids

  • Multiple state objects, or state stored in module-level variables, or state stored only in DOM attributes without a slice backing it.
  • Mutating a slice in place (state.action.text = "foo"). Always build a new slice and install it.
  • Calling a transition during touchmove. Transitions record rest; gestures own motion.
  • Rebuilding a pane's DOM after mount. Use attributes and CSS, or replace a designated list region's contents only.
  • Wiring gestures to dynamic content (card rows, list items, anything that re-renders). Gestures wire to static handles only.
  • Adding addEventListener('click', ...) inside a pane. All clicks go through the layer's delegate.
  • One delegate for the whole application. Each layer has its own.
  • Conditionally omitting elements from render based on state. Render everything; hide via CSS.
  • Two panes claiming the same namespace, or two transitions sharing the same name.
  • Subscribers writing to elements that have data-dragging set, directly or on an ancestor.
  • Stacking action panes on top of action panes. At most one action pane at a time.
  • Reordering layers at runtime. The stack order is fixed (Rule 8).
  • Introducing a framework, a reactive library, or a build-time template system. Vanilla JavaScript, plain functions, plain HTML strings, plain CSS.

Migration notes

This protocol replaces a patchwork of earlier conventions. While the migration is underway, both worlds will temporarily coexist; once the migration is complete, the old shapes are removed without backwards-compatibility shims.

  • Folder layout. The end state has either src/screens/ or src/panes/, not both. During migration, files may live in either; new panes go in whichever folder the migration chooses (recommend src/panes/, since "pane" is the protocol's universal noun). When migration is complete, the unused folder is removed and any remaining files are moved.
  • No backwards compatibility. Once a pane has been migrated to the contract, the previous shape is deleted. Existing files and structures are fair game for renaming, rewriting, or removing — no compatibility shims, no aliases, no deprecated exports.
  • Existing helpers. app.navPane, app.contentPane, and similar ad-hoc method bags are removed as panes migrate. The app.panes namespace introduced recently is also removed in favor of the state machine and per-layer delegates.
  • Gesture factories. The existing src/js/gestures.js factories (wireNavPaneGesture, wireRevealGesture, wireSheetDismissGesture) are replaced or generalized as the new gesture helpers are written. The shape of the new helpers is driven by Rule 6.
  • Bottom-sheet duplication. The bottom-sheet pattern currently duplicated across translation-panel.js, generate-cards-panel.js, and deck-settings.js is extracted into a single action-pane primitive. After extraction, those three modules become content providers for the action pane, not pane scaffolding.

This is version one of the Pane Protocol. It will be revised as the contract is exercised by more panes. Changes to the protocol must come with a migration note in web/AGENTS.md.
