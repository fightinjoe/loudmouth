## Problem Statement

The `/lookup` "directed-graph" prototype (one term → branching related-context groups the
user curates into a phrasebook) felt unsatisfactory for three reasons: (1) too many configs
to set before seeing results (audience, level, VIBE); (2) the branching contexts were not
interesting for conversation; (3) a dictionary / Google-Translate feel sat far from the real
goal — being able to *communicate*. The `proto-textbook-chapter` command (situation → a few
dynamic questions → a whole textbook chapter with words, phrases, grammar nuance, and one
worked conversation) produced output "easily 10x better." The `/textbook` API + a reworked UI
(Figma node 784-20897) now approximate it: ephemeral translation + context questions → a
grouped phrasebook committed whole + a starred-card filter view.

The open problem: with per-card opt-in save removed, how does a phrasebook *grow* — add
words/groups, deepen cards, support different levels — without turning the user into a
librarian, and without losing the conversational, opinionated feel that made the pivot work.

## What Makes This Cool

The unique, defensible use case is **prep** — "I have dinner with my girlfriend's Mandarin-
speaking parents Friday; build me the chapter." Not a dictionary, not a course: a bespoke,
situation-specific chapter generated from a short guided conversation, tuned to the terms you
actually care about, with a two-sided example dialogue. Growing it feels like *continuing that
same conversation*, not operating a tool.

## Constraints

- Minimize cognitive burden: the user must never file, reorder, or regroup to keep a
  phrasebook usable. The app does the bookkeeping.
- Opinionated and bounded: the app has a point of view and then stops. No "slot machine
  lever" the user pulls forever; no fully-editable canvas. Good-and-done over perfect-and-fiddly.
- Conversational continuity: expansion carries the guided-conversation style of creation.
- Thinnest schema (existing API principle 2): prove new richness in `notes` before promoting
  it to a first-class field.

## Premises (all confirmed)

- **P1 — Prep-primary.** The Textbook (prep) job is #1 and the most unique. In-the-moment
  capture is demoted to a *possible future separate mode*, not core UX. This re-weights the
  old BRIEF rather than contradicting it: "primary capture path" there ranked look-up vs.
  import, not prep vs. moment; the branching look-up was always secretly a prep/discovery
  mechanic wearing an in-the-moment costume.
- **P2 — One expansion primitive, three anchors.** "Give me more, here." Anchor decides scope
  *and* filing: group → more cards written into that group's `context`; phrasebook → a new
  section (new `context`); card → *decomposition* (break the phrase into component words +
  grammar), not lateral new language. Auto-filing via the existing `context` mechanism means
  zero user bookkeeping.
- **P3 — No `ability` at initial generation.** Highest-value content is level-invariant (key
  phrases, the conversation example, context-specific vocabulary). Assume basics ("yes/no/
  hello/thank you") are owned unless explicitly requested; spend the whole budget on the
  situation's real vocabulary. (The `/textbook` prompt already gestures at this with its
  floor-as-well-as-ceiling rule; in practice `beginner` still over-produces known basics and
  `intermediate` over-complexifies, so drop the up-front knob.)
- **P4 — Depth & difficulty are on-demand expansions, not settings.** Two axes: *explanation*
  depth (define contained words, explain grammar) and *difficulty* depth (easier/more-advanced
  variants). Both self-served per card. Grammar/word-breakdown is staged in the card `notes`
  blob; some broken-out component words are promotable to their own vocab cards (auto-filed).
- **P5 — Star is bounded priority, not save.** Everything generated is committed; star is a
  binary emphasis so the user can foreground keepers without reordering/regrouping. There is
  no per-card opt-in save.

## Recommended Approach — "Continue the conversation" (menu-first expansion + typing fallback)

Expansion is picking from a small, app-authored, opinionated menu — no typing for the common
case — with a text input always available for a specific ask the menu doesn't cover.

- **The menu is freshly anticipated from what the phrasebook already contains** (generated +
  kept content → what naturally rounds it out), NOT the creation-time checklist.
- **Unchecked checklist items at creation are a *negative* signal** — what the user declined.
  Use them as a *suppression set* for future suggestions (don't re-offer the rejected), never
  as an offer list.
- **Three anchors** (per P2): group "more" generates one bounded, deduped next batch;
  phrasebook "+" offers freshly-anticipated new sections (+ typing fallback); card "break it
  down" produces an opinionated decomposition into `notes` + promotable word cards.
- **No reroll.** A weak result simply goes un-starred; it is never regenerated. The app keeps
  its bias; the user never babysits it.

Cost/shape: reuses `/textbook` call-2 generation, `context` auto-filing, star, and collapsed
sections. Net-new: a scoped "expand" request carrying `{ anchor, existing-content-for-dedup,
suppression-set, optional difficulty nudge }`, and a small "decompose card" call.

### Approaches ruled out during the session
- **A "tap for more" (blank +more button):** too mechanical; loses the conversational feel.
- **B "inspire the unknown":** rejected premise — the job is reaching what the user *already
  cares about without typing*, not surfacing directions they wouldn't have searched.
- **C "regenerable living chapter" (schema-promoted grammar, whole-chapter regenerate):** too
  far — implies no app bias / full editability, and reopens the deferred regenerate/undo
  decision. Perfect as the enemy of the good.
- **D "retain checklist as the expansion menu":** wrong — unchecked items are declines;
  re-offering them pushes the user toward what they rejected.

## Open Questions

- **Volume vs. commit-everything.** Auto-commit + repeated expansion (esp. card decomposition
  → many word cards) grows the phrasebook fast. Star-filter + collapsed sections are the
  intended mitigation; is that enough, or does decomposition need a lighter default (notes-only
  unless the user promotes a word)?
- **Where promoted word cards land.** A per-group "Words" subsection vs. a phrasebook-wide
  vocab group vs. same `context` as the source phrase. Auto-filing rule needs picking.
- **Grammar in `notes` shape.** What structured blob goes in `notes` for a decomposition
  (per-word gloss? particle notes?) before any schema promotion is considered.
- **Difficulty-nudge surface.** How "easier / more advanced" is offered per card without
  becoming a knob (bounded choice vs. a single "rephrase simpler" action).
- **Suppression-set persistence.** Retaining unchecked checklist labels flips the current
  "discard all creation state" decision (J5 Save model); confirm that's acceptable and scope
  what's retained (labels only).
- **Capture mode's future home.** If in-the-moment capture returns as a separate mode, how it
  relates to a prep phrasebook (same object? separate?).

## Success Criteria

- Growing a phrasebook (new group, fuller group, deeper card) requires **no typing in the
  common case and no filing ever**.
- A learner at any level uses the same generated chapter, pulling depth/difficulty per card.
- Initial generation spends its budget on context-specific, conversational, immediately-usable
  language — not on known basics or textbook-stiff complexity.
- The interaction never feels like a slot machine: bounded offers, no reroll.

## Distribution Plan

Existing deployment pipeline covers this — web PWA (Vercel) + Cloud Run API (`api/`). No new
distribution channel; the expansion work is a scoped `/textbook` addition + client UI.
