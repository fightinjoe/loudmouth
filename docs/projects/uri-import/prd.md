# PRD: URI Import

## Problem Statement

Importing cards requires copying a JSON blob from an external tool (e.g., an LLM), switching to the app, navigating to the import panel, pasting into a textarea, and tapping "Parse Cards." On mobile, copy-paste is friction-heavy — the clipboard workflow is clunky, especially when the source is a chat interface. The user wants to click a single link generated by the LLM and land directly in the deck-selection step, ready to confirm the import.

## Solution

Support a URL-based import trigger: when the app loads (or navigates) to a hash URL containing a `?cards=<base64-encoded-JSON>` parameter, it decodes the payload, validates the cards, and opens the deck-selection panel directly — skipping the paste textarea entirely. If the payload is invalid, the app shows an error and falls back to the normal deck view. The user can cancel at any point, returning to the normal deck view.

This allows an external tool (e.g., an LLM) to produce a single clickable link at the end of a card-generation session, making import a one-tap flow on mobile.

## User Stories

1. As a user, I want to click a link containing encoded card data so that I can import cards without copying and pasting JSON.
2. As a user, I want the import link to open the app directly to the deck-selection step so that I don't have to navigate through the import UI manually.
3. As a user, I want to see a summary of how many cards are about to be imported before I confirm so that I know what I'm importing.
4. As a user, I want to select which deck to assign the imported cards to so that my library stays organized.
5. As a user, I want to create a new deck during a URI import so that I don't have to pre-create a deck before clicking the link.
6. As a user, I want to cancel a URI-triggered import so that I can abandon the import without any cards being added.
7. As a user, I want canceling a URI import to return me to the normal deck view so that I end up in a usable app state.
8. As a user, I want the app to handle a malformed or invalid import URI gracefully so that a bad link doesn't leave me stuck.
9. As a user, I want a clear error message when a URI import fails to decode so that I understand what went wrong.
10. As a user, I want the error state to drop me into the normal deck view so that I can continue using the app after a failed import.
11. As a user, I want the URI import to support the same card schema as the paste import so that I can use the same LLM prompt regardless of import method.
12. As a user, I want the URI import to support large card batches (hundreds of cards) so that I can import substantial sets in a single link.
13. As a user, I want the URI import to show a skipped-card count when some cards fail validation so that I know if my import was partial.
14. As a user, I want the deck-selection step triggered by a URI to look and behave the same as the one triggered by paste so that there is no cognitive overhead.
15. As a user, I want the back button / hash change to work correctly after a URI import so that navigation feels natural.
16. As a user generating cards with an LLM, I want the LLM to be able to produce a ready-to-use import link so that the handoff from generation to import is a single tap.

## Implementation Decisions

### URI format

- Import is triggered by a `cards` query parameter in the URL hash: `#deck?cards=<base64url-encoded-JSON>`
- The payload is the same JSON structure accepted by the existing paste import (`{ "cards": [...] }`)
- Base64url encoding (URL-safe alphabet, no padding required) is used to avoid URI encoding issues with large payloads

### Router changes

- The router already extracts query params from the hash; it passes them to `renderDeckView(el, params)`
- No new route is needed — `params.cards` presence signals a URI import
- The router itself does not decode the payload; decoding happens in the screen layer

### Deck-view screen changes

- On mount, if `params.cards` is present:
  1. Attempt to decode and parse the payload
  2. On success: skip straight to the confirm-import panel (deck-selection step), pre-populated with the parsed cards
  3. On failure: show an error toast/message, then render the normal deck view
- The confirm-import panel is the same component/UI used after a successful paste parse — no new UI panel needed; the existing panel is reused
- Cancel button in the confirm panel strips the `cards` param from the hash and navigates to the normal deck view (last deck, or default)
- After a successful import, the `cards` param is stripped from the hash the same way

### URL cleanup after import/cancel

- After import completes or the user cancels, the hash is rewritten to `#deck` (or `#deck?id=<deckId>`) to remove the `cards` param
- This prevents re-triggering the import on refresh or back navigation

### Encoding module

- A small utility module handles encode/decode: `base64url.encode(jsonString)` and `base64url.decode(str) → jsonString | null`
- `decode` returns `null` on any failure (malformed base64, invalid UTF-8) — the caller handles the null case
- This module is pure and has no dependencies — easy to test in isolation

### Validation

- The decoded string is passed through the existing `parseCardBatch()` function — no new validation logic
- Schema normalization (old front/back format) is handled by the existing `normalizeCard()` — no changes needed

## Testing Decisions

A good test exercises the external behavior of a module through its public interface, not its internal implementation. Tests should be pure unit tests where possible (no DOM, no IndexedDB).

### What to test

- **Base64url encode/decode module** — primary candidate for unit tests:
  - Round-trips valid JSON correctly
  - Returns `null` for malformed base64 input
  - Returns `null` for valid base64 that decodes to non-UTF-8
  - Handles empty string, large payloads

- **Import trigger logic (integration-style)** — if tests exist for `deck-view.js` behaviors, add cases for:
  - `params.cards` present and valid → confirm panel opens with correct card count
  - `params.cards` present and invalid → error shown, normal deck view rendered
  - `params.cards` absent → normal deck view rendered (no regression)

### Prior art

- Check `docs/projects/` for any existing test patterns in the project before writing new tests

## Out of Scope

- Generating the import URI — this is done externally (e.g., by an LLM prompt); the app only consumes it
- Sharing links between users — the URI format is designed for personal use (LLM → user's own device)
- QR code generation or scanning
- URI import from the `?` query string on the main URL (non-hash) — hash-based only
- Progressive loading or streaming for very large payloads

## Further Notes

- Browser URL length limits are irrelevant for hash-based URIs — the `#` fragment is never sent to a server. The practical limit is the browser's internal URL buffer (~2MB on most browsers), which is sufficient for thousands of cards.
- If the user is already on the app when they tap the link (e.g., app is open in a background tab), the `hashchange` event fires and the router re-renders — the import panel should open correctly without a full page reload.

### `generate-cards` skill update

After outputting cards, the skill should:

1. Base64url-encode the JSON and produce two import links:
   - **Production:** `https://loudmouth-gilt.verce.app/#deck?cards=<encoded>`
   - **Local:** `http://localhost:8000/#deck?cards=<encoded>`
2. Display the raw JSON automatically below the links (for troubleshooting).

The skill is responsible for the encoding — it should produce `btoa`-compatible base64url output (standard base64 with `+` → `-`, `/` → `_`, padding stripped). Since the skill runs in an LLM context without browser APIs, it must produce the encoding directly in its output step.
